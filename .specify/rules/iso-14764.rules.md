# ISO/IEC 14764:2022 Rules

## Descrição
Define as regras derivadas da norma ISO/IEC 14764:2022 (Manutenção de Software) que todos os agentes devem seguir no processo de manutenção.

## Escopo
- Todos os agentes do sistema
- Todas as skills que tocam no processo de manutenção

## Regras Específicas

### ISO-01: Classificação Obrigatória
**Toda solicitação de manutenção deve ser classificada em uma das quatro categorias:**

| Categoria | Descrição | Gatilhos Típicos |
|:---|:---|:---|
| **Corretiva** | Correção de defeitos | Bugs, exceções, falhas em produção |
| **Adaptativa** | Adaptação a mudanças no ambiente | Atualização de dependências, mudanças em APIs externas |
| **Perfectiva** | Melhorias de desempenho ou manutenibilidade | Refatoração, otimização, redução de dívida técnica |
| **Preventiva** | Prevenção de problemas futuros | Correção de vulnerabilidades, melhorias de confiabilidade |

**Aplicação:**
- O Gateway Agent **deve** classificar usando `classify-trigger.skill`
- A classificação **deve** ser registrada em todos os artefatos subsequentes

### ISO-02: Análise de Impacto Obrigatória
**Antes de qualquer implementação, deve ser realizada uma análise de impacto formal.**

**Requisitos:**
- Identificar todos os artefatos afetados (arquivos, classes, métodos)
- Estimar risco (ALTO, MÉDIO, BAIXO)
- Documentar em `impact-report.md`

**Aplicação:**
- O Impact Analysis Agent **deve** gerar relatório antes de qualquer implementação
- O relatório **deve** ser aprovado por um humano (ponto de checagem)

### ISO-03: Human-in-the-Loop Obrigatório
**Todo plano de mudança deve ser aprovado por um humano antes da implementação.**

**Pontos de Checagem:**
1. **Antes da implementação:** Aprovação do plano de mudança
2. **Antes do deploy:** Aprovação do Pull Request

**Aplicação:**
- O Implementation Agent **não pode** modificar código sem aprovação
- O PR Agent **deve** solicitar revisão humana antes de merge

### ISO-04: Rastreabilidade de Mudanças
**Toda mudança deve ser rastreável até o gatilho que a originou.**

**Requisitos:**
- Cada commit **deve** referenciar o ticket/issue (ex: `#123`)
- O PR **deve** incluir link para a análise de impacto
- O histórico de decisões **deve** ser documentado

**Aplicação:**
- O PR Agent **deve** incluir referências no PR
- Commits **devem** seguir o padrão Conventional Commit com referência

### ISO-05: Validação Obrigatória
**Toda mudança deve passar por validação antes de ser considerada pronta.**

**Requisitos Mínimos:**
- Todos os testes existentes devem passar (100% de sucesso)
- Cobertura de testes não pode diminuir
- Nenhuma regressão detectada
- Análise estática sem violações críticas

**Aplicação:**
- O Validation Agent **deve** executar validação completa
- Se falhar, o PR Agent **não pode** criar o PR

### ISO-06: Preservação da Arquitetura
**Mudanças não podem reestruturar a arquitetura sem autorização explícita.**

**Restrições:**
- Camadas (Controller → Service → Repository) devem ser mantidas
- Padrões de projeto existentes (ex: injeção de dependências) devem ser respeitados
- Mudanças estruturais requerem aprovação de arquiteto

**Aplicação:**
- O Implementation Agent **deve** consultar `architecture-spec.md`
- Violações **devem** ser bloqueadas pela Validation Agent

### ISO-07: Documentação de Mudanças
**Toda mudança deve ser documentada para fins de auditoria.**

**Requisitos:**
- O `impact-report.md` **deve** ser preservado
- O `changes-report.md` **deve** ser gerado
- O PR **deve** incluir descrição detalhada

**Aplicação:**
- O Implementation Agent **deve** gerar `changes-report.md`
- O PR Agent **deve** incluir o relatório no corpo do PR

### ISO-08: Tipos de Manutenção com Prioridades
**Cada categoria de manutenção tem prioridade implícita:**

| Categoria | Prioridade Padrão | SLA Sugerido |
|:---|:---|:---|
| Corretiva (crítico) | Alta | 4 horas |
| Corretiva (não-crítico) | Média | 24 horas |
| Adaptativa | Média | 1 semana |
| Perfectiva | Baixa | 2 semanas |
| Preventiva (crítica) | Alta | 24 horas |
| Preventiva (não-crítica) | Baixa | 1 mês |

**Aplicação:**
- O Gateway Agent **deve** usar esta tabela como referência para priorização
- A prioridade pode ser sobrescrita por humanos

## Exemplos de Aplicação

### Exemplo 1: Mudança Corretiva
- **Gatilho:** NullPointerException em produção
- **Classificação:** ISO-01 → Corretiva
- **Prioridade:** ISO-08 → Alta (crítico)
- **Ação:** ISO-02 → Análise de impacto obrigatória
- **Validação:** ISO-05 → Todos os testes devem passar

### Exemplo 2: Mudança Adaptativa
- **Gatilho:** Atualização do Spring Boot 3.2.0 → 3.2.1
- **Classificação:** ISO-01 → Adaptativa
- **Prioridade:** ISO-08 → Média
- **Ação:** ISO-02 → Análise de impacto (verificar breaking changes)
- **Validação:** ISO-05 → Testes de integração essenciais

## Consequências da Violação

| Violação | Consequência |
|:---|:---|
| Ignorar classificação | Bloqueio pelo Gateway Agent |
| Implementar sem análise | Bloqueio pelo Impact Analysis Agent |
| Pular aprovação humana | Bloqueio pelo Implementation Agent |
| Cobertura de testes diminuir | PR bloqueado pelo Validation Agent |
| Não documentar mudança | PR bloqueado pelo PR Agent |

## Exceções

As seguintes exceções são permitidas:
1. **Hotfixes críticos:** A análise de impacto pode ser simplificada, mas não eliminada
2. **Mudanças cosméticas:** (ex: formatação) podem pular análise de impacto
3. **Documentação:** Mudanças em documentação não seguem as regras de validação
